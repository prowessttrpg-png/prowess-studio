# DIST-WO2 content pack architecture

## Baseline

DIST-WO1 merged in PR #75 at `332639f8b0842aa13b02af27d31d0807908cb924`, tree `f0c944f52678aa0c8b0b61b2ec0162037a4665a3`. All 18 jobs passed in [merged-main CI #275](https://github.com/prowessttrpg-png/prowess-studio/actions/runs/43675523242), including Tier 2 and both installed Windows artifact jobs. The separate manual DIST-WO1 upgrade, recovery, and reboot run was deferred. DIST-WO2 starts on `dist-wo2-content-packs` from that exact commit.

The Release service owns immutable Release identity and the flattened manifest. Its `PROWESS_MANIFEST_V1` digest covers only `entityId:entityVersionId` pins. Content packs add a digest over the actual portable payload. The resolver continues to use the original Release digest and exact references. The v1 pack imports published snapshots through a dedicated persistence path. Local publication still allocates Release and manifest numbers through its governed transaction.

## Portable records

The table specifies the closure to build in a single consistent source read. Prisma models are the storage authority. Compare protected fields by exact identity and normalized values. Reuse only a compatible existing row. Any occupied unique key with a different identity, divergent immutable content, invalid ownership, or unrepresentable dependency blocks the entire install.

| Record / owner | Closure edges and inclusion | Identity, validation and conflict handling |
| --- | --- | --- |
| `RulesetRelease` / Release service | One selected Release. Include its Ruleset, exact flattened manifest, exact policy, and linked ChangeSet. | UUID, Ruleset + number, Ruleset + label, and unique ChangeSet. Verify flattened manifest and composition SHA-256 independently. Preserve Release date, channel and notes. |
| `Ruleset` / Ruleset service | Selected Ruleset and required parent chain. Each record is identity and display metadata. | UUID and global canonical key. Reject lineage cycles and different parents under one identity. Preserve current local name, description, lifecycle status and channel when protected identity matches. Release channel is copied separately. |
| `RulesetManifest`, `RulesetManifestEntry` / manifest service | Selected snapshot plus exact manifests needed by ChangeSet operations. Include entries and follow any included development manifest's parent chain. | Manifest UUID and Ruleset + version. Entry UUID and manifest + Entity. Match each pinned revision to its Entity. Require a parentless Release manifest and validate same-Ruleset operation targets and the actual parent lineage for ancillary manifests. |
| `Entity`, `EntityVersion` / entity and revision services | Exact manifest pins, approved operation/decision references, structured Definition references, and required parent revisions. Resolve Entity identities by UUID. | Entity UUID, globally unique canonical key and EntityType. Version UUID and Entity + revision number. Validate same-Entity lineage, revision state and contents. Preserve display name, rules text and supported stored Definition data. Compare mutable lifecycle status separately. Reject private or mutable draft dependencies that cannot be exported. |
| `EntityAlias` / alias service | Public aliases of selected Release Entities used by compendium search. Do not import unrelated alias collections. | UUID and Entity + normalized alias + normalized context. Validate existing normalization. Preserve conflicting local display metadata and report the collision when required by the pack. |
| `KeywordCategory`, `KeywordDefinition`, `EntityKeyword`, `EntityVersionKeyword` / keyword services | Include assigned Keywords and categories, including exact Keyword keys required by structured Definitions. Follow both identity- and revision-level assignments. | Category and Keyword UUIDs and global canonical keys, assignment composite IDs. Validate referenced category, assignment and Definition vocabulary. Do not rewrite existing deprecated flags or presentation when reusing. |
| `EntityRelationship` / relationship service | Include edges needed by supported reference screens, with both exact endpoint identities. An edge alone never picks the latest revision of another Entity. | UUID and source + target + relationship type. Validate endpoints and allowlisted metadata. Reject a required edge with an unavailable endpoint. |
| `SourceDocument`, `SourceReference` / source and provenance services | Metadata for included revisions, source authorities and conflict candidates. References may point to a snapshot, section, block or table. | UUIDs, source-document and revision ownership, nested location consistency. Preserve approved provenance labels. Exclude filesystem references and private notes or excerpts. Keep optional non-portable anchors as metadata in the provenance snapshot and report any required anchor that cannot be represented. |
| `SourceSnapshot`, `SourceSection`, `SourceBlock`, `SourceTable`, `SourceContentNode`, `SourceAsset`, `SourceAssetPlacement` / M3 source structure | Include only approved metadata necessary to cite supported locations. Do not traverse an entire extracted document from a citation. Required offline images must have separate permitted bytes. | Preserve exact source and location identities in the provenance snapshot. Check snapshot ownership, section ancestry, source hash and applicable ordinals. Do not persist sanitised metadata as an original source-content row or claim a metadata record contains bytes. |
| `CanonPolicy`, `SourceAuthorityRecord` / policy service | Selected policy plus exact policies used by included decisions, each with its authority records and source-document metadata. | UUIDs, Ruleset + policy version, policy + source + scope. Validate policy owner, authority vocabulary and scopes. Preserve source authority statements as provenance. |
| `ChangeSet`, `ChangeSetOperation` / ChangeSet service | Selected Release's ChangeSet and ordered operations. Follow exact optional decision, Entity, from/to revision, and target manifest. | UUIDs and ChangeSet + sequence. Require same-Ruleset ownership, APPROVED linked state and valid operation shape. Preserve reviewed operation identities. |
| `CanonDecision`, `CanonDecisionSelection` / decision service | Exact referenced decision, selected candidate rows, optional result revision, associated policy and conflict. | UUIDs and decision + candidate. Validate policy and conflict Ruleset, decision Entity, candidate ownership and selected revision. Treat source approvals as history. |
| `RuleConflict`, `RuleConflictCandidate` / conflict service | Exact included decisions' conflict and required candidates. A candidate may reference another exact revision and its source reference. | UUIDs and conflict + revision; validate same Entity and candidate/reference version consistency. Exclude unrelated conflicts or unapproved private candidate content. If protected history cannot be represented safely, reject export with the blocking identity. |
| Offline media / asset adapter | Only approved bytes used by supported screens. Store as immutable hash-addressed inert images; a source metadata row is insufficient. | SHA-256, media type, actual size and decoder limits. Preserve byte identity and reject incompatible bytes or type declarations. |

Exclude Characters and all Character-owned tables, `MigrationPlan` and its items, M3 ingestion/extraction/review staging and raw documents, global workspace and deployment configuration, and credentials. Import does not automatically traverse other Releases or all versions. A full R2 pack may carry required R1-era manifests and revisions without installing R1 as a selectable Release.

## Validation and integration boundaries

1. The transport validates a bounded archive and exact byte inventory. It uses a separate pack digest over the manifest and every inventoried file's digest. A valid envelope is only the first validation stage.
2. The transfer service validates protected records, their closed dependency graph, original Release hash and actual Definition content using the existing M5 stored-Definition and exact-reference readers. It owns catalog conflict planning and transactional persistence in `@prowess/db`. It must compare pack and catalog state at commit time and record a single idempotent receipt.
3. Studio serves preview and install through the authenticated local launcher boundary. A claimed creator or category is stored as a claim. Bundled official status requires an approved Release and a pinned digest external to the pack. The first-run sample uses this same validation and installation path. Whole-workspace backup remains a separate format.
4. The installer integration must keep existing demo identities and every Character's exact Release. Create and play tests must compare a receiver Character on R1 before and after importing R2 and after restart. An independent R2-only receiver verifies the closure.

## Implementation

Studio's desktop gateway authenticates the launcher session before allowing export, preview, install, or listing receipts. The hosted endpoints return a refusal. A preview uses a bounded in-memory file and a read-only repeatable snapshot. The install session reacquires the exact file, verifies its digest, serializes competing installs, and compares the relevant catalog state while holding a write-excluding catalog lock. The receipt, portable records, provenance locators and permitted decoded media bytes commit together in PostgreSQL. A retry checks the existing receipt and protected records. Pre-existing compatible local records are reused and retain their local ownership.

The ownership table lists identities inserted by the pack transfer. PostgreSQL guards reject updates and deletes of those rows and prevent ordinary authoring commands from extending owned lineages. The import transaction and validated whole-workspace restore may set a transaction-local transfer mode. This mode never comes from application input. Characters, abilities, play state and play events are outside the transfer store.

The installer exports the isolated WO12 fixture as **Demo — sample rules** and pins its exact Release, archive SHA-256 and content digest. First-run sample setup uses the same preview and install endpoints in a newly migrated workspace before activation. Existing demo saves stay on their original IDs during application upgrade. An official starter still requires an approved source Release and pinned packaged identity.

## Verification

`scripts/distribution/verify-dist-wo2-transfer.mjs` creates independent disposable PostgreSQL databases and moves only `.prowesspack` files between them. It checks deterministic export, exclusion of private data, preview isolation, conflict and receipt failures, replay, ownership, independently installable R2, and live play using R1 and R2. Both Characters are read again from a fresh process. The `--browser` mode runs the production build with the desktop gateway for file selection, preview, install, Character creation, signature ability construction, live play and two restarts. The `--http` mode verifies production requests on a runner without browser support and produces separate evidence. Tier 2 requires the database proof, production browser proof and the manifest gate.
