# Ruleset Foundation (M2-WO1)

**Status: implemented; awaiting its first CI run.** M2-WO1 adds the *identity and
lifecycle* of a Ruleset — nothing more. It has no HTTP API, no UI, and no content.

## What a Ruleset is

A Ruleset is a **named rules universe / configuration lineage**: a stable thing that
exact Prowess content versions will later be selected *under*. Examples of what the
concept is for (none are seeded — tests use synthetic Rulesets only): Core Playtest,
Experimental, Stable, Legacy, a campaign-specific Ruleset.

```
Ruleset                  <- M2-WO1 (this document): identity + status + channel + lineage
    ↓ future (M2-WO2)
RulesetManifest          <- the exact pinned composition
    ↓
Entity → EntityVersion   <- explicit pairs, chosen on purpose
```

| Field | Meaning |
| --- | --- |
| `id` | UUID, opaque, immutable; generated by PostgreSQL (`gen_random_uuid()`) |
| `canonical_key` | required, unique, stable, machine-readable; **the existing CanonicalKey grammar** — no second one |
| `name` | human-facing, required, non-empty after trimming; owned by the Ruleset |
| `description` | optional free text |
| `status` | `DRAFT` (default) · `IN_REVIEW` · `APPROVED` · `PUBLISHED` · `DEPRECATED` · `ARCHIVED` |
| `channel` | `DEVELOPMENT` · `INTERNAL_PLAYTEST` · `CORE_PLAYTEST` · `EXPERIMENTAL` · `STABLE` · `LEGACY` |
| `version_label` | optional human label ("0.1", "Core Playtest 2026.10"); **never parsed as semver** |
| `parent_ruleset_id` | optional self-reference; lineage metadata only |
| `created_at`, `updated_at` | `TIMESTAMPTZ(6)`; same conventions as `entities` |

## Why a Ruleset holds no Entity membership

A Ruleset deliberately references **no Entity and no EntityVersion**. There is no
`ruleset_id` on `entity_versions`, and a static audit plus a live-database column
check both fail if one appears. The relationship is many EntityVersions selected
*through a manifest*, which is a separate, explicit record (M2-WO2). Putting a
convenience column on EntityVersion would be architecturally wrong: an EntityVersion
is a historical snapshot that can appear under many Rulesets.

## Why the latest revision is never implicitly selected

A Ruleset's contents must **not** be derived from any of:

- the latest EntityVersion (highest revision number);
- CANON status alone;
- the highest revision number;
- Source authority alone.

None of those determines which rule applies — M1 proved they are each *descriptive*.
So there is no field anywhere equivalent to `current_entity_version`, `active_rule`,
`global_current_rule`, `use_latest_version`, `automatic_latest` or
`current_manifest_entry`. The static audit scans the Ruleset schema, domain code,
persistence code, and migration for those identifiers, and also fails if Ruleset
code even *mentions* `latestRevision`, `revisionNumber`, `authorityStatus`, or
`EntityVersion`. M1's rule — "latest revision is a list-display convenience, not
Canon or Ruleset resolution" — is preserved.

## Status and channel are not Canon authority

`status` and `channel` are descriptive governance metadata. A Ruleset that is
`APPROVED`, or on the `CORE_PLAYTEST` channel, **does not make any EntityVersion
Canon**, publishes nothing, selects nothing, and changes no mechanic. Nothing in the
system behaves differently based on either value in M2-WO1.

`RulesetStatus` is **its own vocabulary**, not `EntityVersionStatus`: they share five
labels (`DRAFT`, `IN_REVIEW`, `APPROVED`, `DEPRECATED`, `ARCHIVED`) but describe
different things — an EntityVersion's status is the maturity of one piece of content;
a Ruleset's status is the governance state of a whole configuration. `PUBLISHED` exists
only for Rulesets, while `PLAYTEST`, `CANON` and `SUPERSEDED` exist only for
EntityVersions. A unit test pins exactly that overlap.

**Creation is always `DRAFT`.** `CreateRulesetInput` has no `status`; the service
assigns it, so no caller can mint a `PUBLISHED` Ruleset (a test smuggles one in and
confirms it is ignored). There are no publishing or status-changing operations yet.

## Parent lineage

`parent_ruleset_id` records that one Ruleset descends from another (Core Playtest →
Experimental). **It is metadata only** in M2-WO1: nothing inherits manifest contents
and nothing resolves content through a parent. Inheritance *semantics* are explicitly
deferred.

- The parent is chosen **at creation** and no operation changes it — there is no
  update API, so lineage is creation-time metadata for Phase 1.
- The parent must exist → otherwise `RULESET.INVALID_PARENT` (a malformed id is the
  same, never a raw database error), and nothing is persisted.
- Self-parenting and lineage loops (`A → A`; `A ← B` then B as A's parent; the deeper
  `A ← B ← C` then C as A's parent) → `RULESET.PARENT_CYCLE`.
- The parent foreign key is **`ON DELETE RESTRICT`**: a parent cannot be physically
  deleted while a child references it. No delete operation is exposed.

**Why the cycle check exists although nothing can currently trigger it.** A brand-new
Ruleset has no id yet, so at creation it can be neither its own parent nor anyone's
ancestor — the check is vacuous there. It is built now (a pure function in
`@prowess/model`, with a persistence-backed validator in `@prowess/db`) so that any
future operation that *changes* a parent is protected from day one, and it is
unit-tested independently and integration-tested against real rows. A future mutating
operation must run the validator inside a transaction that locks the ancestor chain;
that is noted in the code. No update API was added just to manufacture a cycle.

**Two error codes, deliberately.** `INVALID_PARENT` = the named parent doesn't exist
(a bad reference; pick another id). `PARENT_CYCLE` = the parent exists but the
assignment would make a loop, including self-parenting (the lineage itself is the
problem). Merging them would force callers to parse a message to learn which.

## Operations

`@prowess/db` exposes exactly four: `createRuleset`, `getRuleset`,
`findRulesetByCanonicalKey` (returns `null` when absent, like Entity), and
`listRulesets` (ordered `canonical_key ASC, id ASC`; optional validated `status` /
`channel` filters). The persistence internals (`insertRuleset`, `selectRulesetById`,
`selectRulesetByCanonicalKey`, `selectRulesets`, `selectRulesetAncestors`) stay
inside the package.

## Errors

| Code | Meaning | HTTP (reserved — no route yet) |
| --- | --- | --- |
| `RULESET.NOT_FOUND` | by-id lookup found nothing (incl. malformed id) | 404 |
| `RULESET.CANONICAL_KEY_CONFLICT` | key already used | 409 |
| `RULESET.INVALID_INPUT` | malformed key / blank name / unknown channel / blank label / bad filter | 400 |
| `RULESET.INVALID_PARENT` | parent does not exist | 400 |
| `RULESET.PARENT_CYCLE` | would create a lineage loop (incl. self) | 409 |

The HTTP statuses are recorded in the central, compile-time-exhaustive map now even
though there is no route: adding a known error code without choosing its status is a
type error by design (this was verified for these codes), and a future route should
not have to retrofit it. A duplicate key is recognized by **constraint name**
(`rulesets_canonical_key_key`), the same shared detector M1 needed for the Prisma 7
driver adapter.

## Database conventions (identical to M1, enforced by the blocking drift gate)

- UUID id: `DEFAULT gen_random_uuid()` in the migration **and**
  `@default(dbgenerated("gen_random_uuid()"))` in `schema.prisma`.
- `created_at`: `DEFAULT CURRENT_TIMESTAMP` ↔ `@default(now())`.
- `updated_at`: **no** database default ↔ `@updatedAt` alone (same as `entities`).
- One migration, `20261004233000_add_ruleset_foundation`: two enums, one table, the
  unique canonical key, an index on the parent, and the `RESTRICT` self-reference. No
  manifest tables.

The static audit checks the schema against the migration SQL structurally (id default,
and — for every `@updatedAt` field — default presence), and the CI step
`prisma migrate diff --exit-code` must report no differences.
