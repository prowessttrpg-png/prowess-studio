# DIST-WO1 desktop architecture

The supported target is Windows 11 x64 in an ordinary user account. The installed launcher is a Go executable using Win32 for the window, default browser, per-user lifecycle lock, and process job. NSIS supplies the per-user installer and shortcut. This choice uses the Go standard library and Windows APIs for process ownership and leaves the application in Next.js. A WebView or Electron would add a desktop renderer to a browser-based requirement. A PowerShell launcher would make a shell part of ordinary startup.

The per-user installer builds a versioned directory from a verified archive and activates it after extraction. The Go extractor uses Windows long-path-aware file operations and checks archive identity, regular files and relative paths. The installer preserves the previous binary directory and keeps all player data in a separate directory. It does not install a Windows service.

The launcher serializes lifecycle operations with a file lock and starts the Node controller in a Windows job before allowing it to start children. A second launcher invocation requests a fresh browser launch from the existing controller. Node runs the bundled PostgreSQL 16.14, Prisma schema engine, production Next.js standalone server, and loopback gateway. The controller can choose distinct ephemeral ports and confirms database path, version, persistent ownership, migration status, and a live Studio query. PostgreSQL binds IPv4 loopback and uses generated SCRAM credentials. The runtime and its data stay under the account's local application data directory. The launcher makes an account-local DOS drive mapping when PostgreSQL needs an ASCII access path.

The browser gateway requires the expected loopback Host and blocks cross-site fetch metadata and mismatched Origin. Mutations require the exact Origin. The native launcher exchanges a separate control credential for a short-lived, single-use URL fragment. The browser removes the fragment before exchanging it for an HTTP-only SameSite Strict session cookie. The gateway authenticates all Studio and workspace requests and supplies a separate credential to the Next.js desktop-only proxy. Hosted and developer operation retain the original configuration. This boundary assumes the ordinary user account and browser are trusted, and local malware operating under that account can access the account's files and processes. Browsers scope cookies to the loopback host across ports.

Backups contain a versioned, checksummed snapshot of application rows read in one PostgreSQL repeatable-read transaction. The backup includes portrait byte columns, exact Character and rules references, abilities, resources, and event data. It omits machine credentials and the separate PostgreSQL maintenance ownership record. The current envelope has a 256 MiB limit. It accepts the shipped table and column layout and restores parameterized values into a separately migrated database with foreign keys checked before cutover. A second installation creates its own identity and credentials. Restore writes a recovery backup first and invalidates browser sessions when the active database changes.

Upgrade checks the recorded and actual migration history before a recovery snapshot. It migrates a database copy, checks the schema and launches Studio on the copy before updating the active pointer. The old database and previous binary directory remain available for recovery. PostgreSQL major changes and application downgrades are refused. The recovery journal records the previous and staged database names and backup filename for an interrupted upgrade.

The demo is prepared from the existing guarded WO12 fixture in a disposable build-time database. Installation contains a data backup with Release provenance. The player chooses whether to import it through the same staging and validation boundary used for a workspace restore. No mechanics package owns distribution logic.
